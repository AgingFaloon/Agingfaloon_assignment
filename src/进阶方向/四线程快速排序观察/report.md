# 四线程快速排序观察

下面关于线程、划分和正确性的结论都来自本地自行编译、运行和核对。

## 总结

- 用 C++17 `std::thread` 实现快速排序：五数取中基准 + 三路划分，区间长度 ≤ 3 时改插入排序。
- 每次排序期间线程总数上限 4（main + 最多 3 个由 `std::thread` 创建的子线程）；名额不回收，故同一时刻 ≤ 4 个与一次排序累计创建 ≤ 3 个同时成立；所有子线程都由父线程 `join`，`main` 返回前全部汇合。
- 对 `data.txt` 的 16 个整数排序结果：`0 3 7 7 15 15 19 23 36 42 42 54 61 88 91 100`，与 `std::sort`、C 标准库 `std::qsort` 和 Python `sorted()` 的结果一致。

## 线程

### 所选线程库

选择 C++17 标准库 `std::thread`，只用到 `<thread>`、`<atomic>`、`<mutex>` 等标准头，没有使用 OpenMP、TBB、MPI 或 CUDA。Linux 上用 `g++ -std=c++17 -pthread` 编译，Windows 上用 `cl /std:c++17`。（Windows 本地版本另外用 `<windows.h>` 的 `SetProcessAffinityMask` 绑定 CPU，只用于测量，不参与排序。）

### 工作线程的创建位置和数量上限

唯一的创建点是递归函数 `quicksort_parallel()`（`main()` 里只调用它一次）。它先做一次划分，然后把**较大的子区间**交给 `std::thread`，自己继续处理较小的子区间：

```cpp
// quicksort_parallel() 内的创建片段
if (bigLen > kSerialCutoff && try_spawn_worker()) {
    std::thread t([&a, bigLo, bigHi, depth] {
        quicksort_parallel(a, bigLo, bigHi, depth + 1);   // 子线程做自己的区间
    });
    if (smallLen > 0)
        quicksort_parallel(a, smallLo, smallHi, depth + 1); // 父线程做小的那边
    t.join();                                               // 等子线程结束
    return;
}
```

`main()` 里没有其他 `std::thread`，也没有用 `std::async`、`std::jthread` 或线程池。

用一个“只增不减”的全局计数器加 CAS 抢名额：

```cpp
constexpr int kMaxSpawned = 3;                 // main + 3 个子线程 = 4 个线程
std::atomic<long long> g_spawned{0};

bool try_spawn_worker() {
    long long cur = g_spawned.load(std::memory_order_relaxed);
    while (cur < kMaxSpawned) {
        if (g_spawned.compare_exchange_weak(cur, cur + 1, std::memory_order_relaxed))
            return true;                       // 抢到名额
    }
    return false;                              // 名额用完：当前线程串行处理
}
```

- 名额**不回收**：子线程结束也不归还名额。所以保证的不仅是“同一时刻 ≤ 4 个”，而是**每次排序期间创建的子线程总数 ≤ 3 个**（加上 `main` 共 ≤ 4 个线程）
- **口径边界**：main()` 里的自测循环（8 个用例 + 1000 次复核 A + 100 次复核 B）会在整个进程里累计创建约 2,300 个线程，那是自测框架的行为，不在题面的单次运行口径内。
- 抢不到名额时，当前线程把两个子区间直接按串行递归处理，不再创建线程；`std::thread` 构造抛异常时把名额退回（`g_spawned.fetch_sub(1)`）并退化为串行，避免名额泄漏。
- 没有 `detach()`：每个子线程都由创建它的父线程 `join`，`join` 在子线程对象离开作用域之前完成。

### 实测

- 16 个数：`main` + 2 个子线程 = **3 个线程**（16 个数先划成 9 / 2 / 5，9 个那段再划成 4 / 2 / 3；4 个元素的那段划分后两侧都 ≤ 3，不需要再开线程）。
- 1000 个随机数、4096 个已升序/已降序、100000 个随机数：`main` + 3 个子线程 = **4 个线程**，累计创建的子线程正好 3 个，没有超过上限。
- 每次排序结束后程序检查存活线程数回到 1（全部 join），所有用例都通过；16 个数重复 1000 次、1000 个随机数重复 100 次，都没有出现单次排序超过 4 个线程、或单次排序累计超过 3 个子线程的情况。

（单 CPU 上子线程完成得很快，本次观测到的存活线程峰值是 3 个；上限 4 由计数器保证，不依赖是否观测到 4 个同时存活。这里的“上限”都指**单次排序**，不含自测循环的进程总量。）

## 划分与汇合

### 基准和划分数据

- 基准取**五数取中**：在区间里取 5 个等距位置（`lo`、1/4、1/2、3/4、`hi`），把这 5 个值排序后取中位数，只取数值、不搬动元素。
- 取 5 个采样点而不是 3 个（`lo`、`mid`、`hi`）的理由：三数取中在“整体有序、但端点有少量错位”的区间上会取到偏小或偏大的值，划分会一边倒。本地实测中，对 4096 个已升序/已降序元素用三数取中时，递归深度会撞上 32 层安全阀；改成 5 个采样点后，所有用例的深度都在 16 层以内，安全阀触发次数为 0。
- 本题 16 个数在根区间的 5 个采样值是 `42, 42, 7, 23, 100`，排序后中位数是 **42**，与后面的划分轨迹一致。

```cpp
// 取区间内 5 个等距位置的值，排序后取中位数
int median5(const std::vector<int>& a, int lo, int hi) {
    const int n = hi - lo + 1;
    int v[5];
    for (int t = 0; t < 5; ++t)
        v[t] = a[lo + (n - 1) * t / 4];
    for (int i = 1; i < 5; ++i) {              // 5 个数直接插入排序
        int key = v[i], j = i - 1;
        while (j >= 0 && v[j] > key) { v[j + 1] = v[j]; --j; }
        v[j + 1] = key;
    }
    return v[2];
}
```

- 划分用三路划分（荷兰国旗），一趟扫描把区间分成三段，等于基准的整段不再递归：

```cpp
// [lo, lt) < pivot；[lt, gt] == pivot；[gt+1, hi] > pivot
int three_way_partition(std::vector<int>& a, int lo, int hi, int& lt, int& gt) {
    const int pivot = median5(a, lo, hi);
    int i = lo; lt = lo; gt = hi;
    while (i <= gt) {
        if (a[i] < pivot)      { std::swap(a[lt], a[i]); ++lt; ++i; }
        else if (a[i] > pivot) { std::swap(a[i], a[gt]); --gt; }
        else                   { ++i; }
    }
    return pivot;
}
```

- 这样重复元素（本题的 42、7、15 各出现两次）一次划分就全部就位，不会退化成 O(n²)；`4096 个全相同元素` 的用例只做一次划分就结束，没有再创建线程。

### 串行截止条件

- **区间长度 ≤ 3** 时不再划分，直接插入排序（`insertion_sort`）。
- 另外设**递归深度 ≥ 32** 作为安全阀：即使遇到病态输入也强制转串行，避免递归过深；本次所有用例的最大深度只有 16（4096 个已升序/已降序），安全阀触发 0 次。
- 取 3 的理由：题面数据只有 16 个数，阈值再大就几乎没有并行度；区间 ≤ 3 时插入排序的常数比“再划分 + 递归”小。题面允许用区间长度或深度作为截止条件。

### 工作线程的汇合位置

- 汇合点在 `quicksort_parallel()` 内部：父线程创建子线程后，先处理较小的子区间，然后在函数返回前 `t.join()`。`t` 是局部变量，`join` 之后才离开作用域。
- 子线程返回前也会 join 它自己创建的子线程，所以形成一棵 join 树。`main()` 调用的 `quicksort_parallel()` 返回时，它的直接子线程已经 join；又因为每个父线程都 join 了自己的子线程，所以此时所有后代线程都已结束。
- 每次运行后检查存活线程数回到 1。

## 正确性

### 验证方法

程序对每个用例排序后做四项检查，全部通过才算该用例成功：

1. **相邻逆序检查**：`std::is_sorted` 为真，并统计相邻逆序对数量，必须为 0。
2. **与 std::sort 对比**：复制同一份输入用 `std::sort` 排序，结果逐元素相等。
3. **与 C 标准库 qsort 对比**：再用 `std::qsort` 排一份，结果逐元素相等。
4. **线程检查**：排序结束后存活线程数回到 1（全部 join）；累计创建的子线程数 ≤ 3；存活线程峰值 ≤ 4。

程序外再用 Python 的 `sorted()` 独立算一遍期望值，和程序输出逐元素对比。

### 验证结果

- 题面 16 个数：
  - 输入：`42 7 19 42 3 88 15 7 61 0 54 23 91 15 36 100`
  - 输出：`0 3 7 7 15 15 19 23 36 42 42 54 61 88 91 100`
  - 相邻逆序对 0；与 `std::sort`、`std::qsort`、Python `sorted()` 完全一致；7、15、42 各 2 个，数量与输入一致。
- 其余用例全部通过（摘要）：

| 用例 | n | 结果 | 创建子线程 | 最大深度 | 耗时（观察） |
|---|---|---|---|---|---|
| data.txt 的整数 | 16 | 有序，三种参考一致 | 2 | 3 | 0.09–0.10 ms |
| 随机数 [0,100] | 1000 | 有序，三种参考一致 | 3 | 9 | 0.20–0.22 ms |

| 单元素 / 两元素逆序 | 1 / 2 | 有序，三种参考一致 | 0 | 0 | < 0.001 ms |

- 重复复核：
  - 16 个数重复 1000 次：1000/1000 次结果正确，存活线程峰值最大 3，从未超过 4。
  - 1000 个随机数重复 100 次：100/100 次正确，存活线程峰值最大 3，累计创建子线程 3 个，从未超过 4。

耗时列只是墙钟观察，见“环境限制”，不作性能结论。

## 环境限制

- 题面给的沙盒只有 **1 个 CPU**。本报告的本地运行也只在 **1 个逻辑 CPU** 上完成（启动时用 `--cpu0` 把进程绑定到单个逻辑 CPU）；所有 `std::thread` 线程共用这一个核，操作系统只能分时切换，没有真正的并行执行。
- 所以表里的耗时只是**观察记录**（16 个数 0.1 ms 左右，100000 个数 2.2–2.7 ms 左右，包含线程创建和切换的开销）。它**不能解释为加速成绩，也不是性能得分**；报告不给出加速比，也不拿它和串行版本做排名。
- 单 CPU 上，16 个数这种规模做并行并不划算（线程创建开销远大于排序本身）。线程机制在这里的意义是把“线程数上限、划分方式、截止条件和汇合位置”写清楚，而不是提速。
